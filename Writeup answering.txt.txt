1. What is the difference between an access token and a refresh token? Why are they different expiry lengths?
The access token is what actually gets sent with every API request to prove who you are — it's short-lived, 15 minutes in my app. The refresh token's only job is getting a new access token from `/api/refresh`, and it lasts much longer, 7 days. They're different lengths on purpose: the access token expiring fast limits how long a leaked token stays dangerous, while the refresh token stays long-lived so the user doesn't have to log in again every 15 minutes.

2. What is an Axios interceptor and why is it better than manually adding the token to every API call?
An interceptor is a function that runs automatically before every request goes out or after every response comes back, without me having to call it manually. In my `api.js`, the request interceptor attaches the `Authorization: Bearer <token>` header to literally every call by itself — so I never had to go back and edit Home.jsx, Cart.jsx, Checkout.jsx, or any other page individually. If I'd done it manually, I'd have to remember to add the header in dozens of places, and forgetting even one would silently break that request.

3. What happens in your app when the access token expires mid-session? Walk through the exact sequence of events in your interceptor code.
The expired token gets sent as usual, the backend rejects it with a 401, and my response interceptor catches that 401 automatically. It then grabs the refresh token from localStorage, calls `/api/refresh` with it to get a brand new access token, saves that new token, and retries the exact original request — all silently, so the user never even notices anything happened. Only if the refresh call itself fails (refresh token also expired or revoked) does it clear everything and redirect to `/login`.

4. What is the difference between JWT authentication and Flask session authentication? Why is JWT better for a React single-page application?
Sessions are stateful — the server has to remember every logged-in user in a session store, and the browser proves who it is with a cookie. JWT is stateless — the token itself carries the user's identity and role, signed so it can't be faked, and the server just verifies the signature without looking anything up. This suits a React SPA better because the same token works identically whether it's a web app, a mobile app, or some other API client, and it scales across multiple servers without needing a shared session store.
